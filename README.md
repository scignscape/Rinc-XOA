
# RedPatch : Research Objects - Diamond Open Access Targeting Community Health

RedPatch is Community Health-oriented research platform with C++ sublibraries related to Electronic Health Records, Medical Imaging, Geographic Information Systems, and Academic Publishing.

---

First, a disclaimer: the code linked from this branch originated with my own personal research project or ones I joined as a programmer and/or (data and text) editor.  There is no funding nor development team.  As such, this work is less polished than I would like, and all code should be considered prototype/experimental.  I appreciate anyone who actually browses this code, but in practice I may need to personally help interested users (on a volunteer bases) to adapt this code for their own projects, at least during this early stage (at least I HOPE this is just an early stage!).  This is true of RedPatch itself and the more general libraries it references (grouped into the `DogLeash` repository which is sibling to the current "`Rinc-XOA`" -- "Research in nonprofit contexts -- Executable Open Acccess" repo).

So, RedPatch is the *early stages* of a Research Platform for Community Health.  It is part of a larger project that involves code supporting Diamond Open Access publishing in general -- i.e., neither Article Processing Charges (APCs) for authors nor paywalls for users, releasing scientific research via licences typically associated with Free and Open-Source (FOSS) software -- particularly *Executable Research Objects* that cross-reference documents with open-access data sets (integrated into a single package and, indeed, once compiled, into a single Research Application).

---

## Overview

The underlying technology I have called "DogLeash" (Diamond Object Grid - Language Server and Script Host) which develops Executable Research Objects as collections of semi-autonomous modules.  RedPatch is one instantiation of this idea, combining several modules related to Community Health.  These modules are split between the DogLeash repository itself (for more general-purpose code) and this current branch.  More precisely, RedPatch is comprised of six modules:


- Academic Publishing: document preparation and data integration

- Electronic Health Records -- including special-purpose records/forms that might be specifically used by Community Health researchers 

- Medical Imaging, to support researchers studying community-health providers in areas of medicine where imaging is important for diagnosis and treatment, such as Oncology, musculoskeletal interventions, and prenatal care

- Digital Maps to build, export, and visualize GIS data sets addressing community-health concerns such as disease outbreaks, epidemiology, Social Determinants of Health (SDoH), and locations of health-care providers (permanent or temporary/emergency)

- Environmental Factors: tools to study public-health implications of pollution, ecological degradation, contaminated water supplies, and similar civil-infrastructure concerns

- Compiler Infrastructure: Supporting programming tasks such as implementing new EHR forms for individual research projects

---

To be more specific, the modules include code that may be narrow in scope but could be adapted for other contexts.  For example, the `EHR` module is focused on `AMPATH` (Academic Model Providing Access To Healthcare) Forms but the implemented "native rendering" techniques could be used with other `EHR` systems.  Here is concrete functionality representative of the aforementioned modules:

- Academic Publishing:  RedPatch incorporates the `DogLeash` `GTagML` module, which can be used to generate documents in a variety of formats, including `PDF`, `LaTeX`, and `JATS-XML`.  `GTagML` is optimized for creating publications that are cross-referenced with data sets in Executable Research Objects.  See the GTagML branch of DogLeash at [https://github.com/scignscape/DogLeash/tree/GTagML](https://github.com/ScignScape/DogLeash/tree/GTagML).

- Electronic Health Records: At present, this module (`RedPatch-EHR`) is focused on a "Native Rendering Engine" for `AMPATH` forms.  In `OpenMRS` (Open Medical Record System) -- developed by `AMPATH` and used by Doctors Without Borders, Partners in Health, Care 2 Communities, and other `NGO`s/nonprofits -- `AMPATH` forms are internally stored as `JSON` configuration files that get converted to web pages via `ReactJS`.  This module provides an alternative rendering engine that, instead, maps the configurations to C++ classes to provide self-contained `GUI` components.  These classes could be run as isolated executables, or grouped into form libraries that collectively form customized `EHR` software, or embedded in host applications.  But in each case the form is a single desktop application window: there's no need for client/server separation, server processes, `HTTP` requests, or running the User Interface through a web browser.

    `AMPATH` forms are granularly annotated, particularly via Open Concept Library (`OCL`) concepts (which often cross-reference with other terminology standards, such as `CIEL` (Columbia International eHealth Laboratory), `SNOMED`, and `ICD` (International Classification of Diseases)).  Form fields and (for enumerative values) their possible values are assigned unique `OCL` identifiers, as are forms as a whole and their component sections.  These annotations are presevered via the Native Rendering Engine as `C++` source annotations and `GUI` metadata.

    `OpenMRS` has also proposed an "`Annotation`" module that applies to `EHR` forms connected with medical images.  On this proposal, external imaging software would be launched and result in either manual or automated annotations that get merged into base images and saved in conventional picture formats; those files may then be included in `OpenMRS` forms as "`Attachments`".  Via `RedPatch`, that workflow can be simplified: forms become `C++` classes that may be embedded within imaging software, which is a host application rather than external process to be launched separately.  As a result, there is no data marshaling, just ordinary calls between `C++` procedures.

    For reference and demonstration purposes, the `RedPatch-EHR` module includes generated code for the 77 `AMPATH` Forms developed by Doctors Without Borders; other forms may be customized via the `OpenMRS` form builder.  The module's utilities generate a `C++` class from `JSON` configuration files, and demo code shows how to perform these steps for each of the Doctors Without Borders form files.

- Medical Imaging: Most of the `RedPatch` code for diagnostic imaging is based on the `C++` library `DCMTK`, one of the most widely used libraries for processing `DICOM` (Digital Imaging and Communications in Medicine) files.  `RedPatch` provides several programs that follow the same protocol as other `DCMTK` utilities, either invoked from the command line or called as ordinary C++ methods from host applications.  `RedPatch` code includes:

    &nbsp; &nbsp; &#x2192; dcm2cdm: Represent `DICOM` metadata in terms of the `MI-CDM` (Medical Imaging Common Data Model) proposal from `OMOP` (Observational Medical Outcomes Partnership).  `OMOP-CDM` embraces a tabular structure in contrast to standards such as FHIR (Fast Healthcare Interoperability Resources), which means that data objects have to be exported via `OMOP`-specific algorithms

    &nbsp; &nbsp; &#x2192; dcm2ro: Construct Research Object components conformant to specifications such as `RO-Crate`.  This utility packages select `DICOM` images, metadata such as `GSPS` (Greyscale Presentation State), and `DICOM-SR` (Structured Reporting) files into single resources using generic formats such as `PNG` and `XML` instead of `DICOM`-specific encoding.  The resulting files can be packages into Executable Research Objects and other dataset protocols.

    &nbsp; &nbsp; &#x2192; dcm2qt: Exports `DICOM` images and annotations in a format recognized by `QGraphicsScene` (part of the `Qt/C++` `GUI` library).  Annotations thereby may be converted to `QGraphicsSceneItem` objects.

    &nbsp; &nbsp; &#x2192; dcm2lsp: Encapsulates information about `DICOM` classes in structures suitable for coding tips and assistence within code editors and Integrated Development Environments (`IDE`s).  This utility conforms to the Language Server Protocol, which is the predominant standard for implementing code analyzers that work in consort with `IDE`s, and may be of help for projects that seek to implement new `C++` classes managing `DICOM` data in custom ways.
 
    In addition to these utilities, `RedPatch` provides sample code to show how the utilities and `AMPATH` native-rendered forms may be embedded in `DICOM/PACS` (Picture Archive and Communications System) software.  More spefically, `RedPatch` publishes plugins to `medInria`, and open-source, full-featured `Qt/C++` `DICOM` client with an emphasis on advanced image-processing capabilities.

- `GIS` and Digital Maps: The `DogLeash` `Qt-OpenStreetMap` module provides tools for working with `OpenStreetMap` tiles within the `Qt/C++` GUI library.  Digital Cartography is based on map tiles, which are small image files that represent one portion of a street or topographic map at a specific resolution (i.e., zoom level).  A complete map is composed by splicing together multiple tiles, typically in the range of 10-20; as users pan or zoom the map new tiles are introduced and others become invisible.  Digital Cartography software is designed to download tiles from sources such as OpenStreetMap but also cache tiles that may be reused -- once someone browses maps in a given geographic area they tend to return to the same area multiple times.

    In a `Qt` environment, map tiles are rendered not as isolated images but part of a `QGraphicsScene`.  Geographic Information Systems databases -- which are generically called "Attribute Layers" -- are essentially any collection of records that are indexed by latitude/longitude pairs or other `GIS` coordinate systems.  In `Qt`, `GIS` attribute points are mapped to locations in the current `QGraphicsScene` (which depends on the active zoom level and pan position), and attribute layers may be rendered by introducing coded `Qt` graphics objects at each resulting point; these objects are assigned informative colors and shapes to visually indicate what sort of building or feature is of interest at that latitude/longitude coordinate pair.  Semi-transparent and/or patterned overlays can likewise be introduced to convey information which is not localized to single points; for example, a "heat map" summarizing a disease outbreak. 

    `Qt-OpenStreetMap` technology is not specific to Community Health, but `RedPatch` can provide symbol/icon protocols informed by the kind of `GIS` locations that might be of interest to Community Health researchers, such as clinic locations, gradients showing the prevalence of a disease, or `GIS` maps of environmental factors that may contribute to poor health outcomes.

    The `DogLeash` `GIS` module also contains demo code documenting how to create special-purpose map tiles.  While many organizations load tiles from generic sources such as `OpenStreetMap`, it is possible to customize the appearance of tiles depending on how the maps are used.  All tiles show similar features -- these are base maps on which Attribute Layers are overlaid, so they do not represent any locations specific to a single GIS data set -- but there are a range of options for visual styling, such as which colors are used for roads, waterways, buildings, topographic features, and other civil infrastructure.  Styles include both colors and line shapes/patterns for single-dimensional constructions, such as representations of roads or railways.  Organizations may find it worthwhile to create their own styles which visibly emphasize features that are of interest to them (and use more muted coloring/patterning for other features).  Custom styles for large geographic regions may be impractical because they demand large server archives, but tile customization is feasible for projects where users will typically focus on a few relatively compact areas (e.g., cities where a nonprofit is operating).  Generic tiles can always be used for coordinates outside these customized locations.  When "bespoke" tiles are used, they can be distributed with the `GIS` application rather than having the organization maintain its own Tile Server; in this case the front-end needs to check if a given coordinate location can be matched to the custom tiles, bypassing the typical server/cache protocol.  `DogLeash` has sample code showing how this might be programmed. 

- Environmental Factors:  The `RedPatch-EF` module, part of this current branch, provides code supporting research into environmental hazards (e.g., carcinogens or other pollutants) that have a measurable, deleterious impact on Community Health.  There are many publically accessible data sets indicating the measured or reported presence of harmful chemicals, and these data sets may be statistically cross-referenced with medical records.  For example, ProPublica has published multiple studies documenting correlations between industrial waste products and cancer diagnoses in several US jurisdictions.

    A good example of environmental-hazard data sets -- and one this module references for demonstration -- is the United States Environmental Protection Agency "Toxic Release Inventory" (`TRI`); this was the source studied by `ProPublica` in reports such as (How We Created the Most Detailed Map Ever of Cancer-Causing Industrial Air Pollution)[https://www.propublica.org/article/how-we-created-the-most-detailed-map-ever-of-cancer-causing-industrial-air-pollution].  This complex data set, which may be downloaded individually by state, has over 200 columns describing self-declared leaks/contamination that companies (which handle potentially toxic substances) produce as mandated by federal law.  Like most environmental data resources, it is implicitly a `GIS` data set that pinpoints locations of possible contamination.  Multiple reports in a similar area, sustained over time, indicate hazards which could impact public health, so analyzing `TRI` data is one part of potential workflows that also map out `EHR` records with respect to patients' home (or work) locations.  The `TRI` data model employs flat-file structures to represent partially-hierarchical data (there is no one-to-one correspondance between columns and data fields/parameters), which means relatively complex parsers are needed to assemble `TRI` reports into a usable form.  `RedPatch-EF` implements those parsers with code that could hopefully be reused on the context of other environmental data sets.

    The other primary component of `RedPatch-EF` is a plugin to `IQmol`, a molecular-visualization application, which can serve as an example of embedding `RedPatch` components into scientific platforms (particularly software written in `Qt/C++`).   The idea behind this `IQmol` embedding is that visualizing atom-scale structurs can help clarify what makes certain compounds harmful for people, animals, and/or ecosystems (carcinogens, "forever" chemicals, etc.).

- Compiler Infrastructure: The `Qynviper-ChasmVM` module has code related to both C++ interop and special-purpose Virtual Machines which might be embedded in Executable Research Objects (for the record, "`Qynviper`" is "Query/Native Interop for Executable Research" and "`ChasmVM`" is "Channel/Syntagm Virtual Machine").  In RedPatch, I have primarily used this code so far for the AMPATH form processor (and code generator).  The main `Rinc-XOA` branch (i.e., [github.com/ScignScape/Rinc-XOA](https:www.github.com/ScignScape/Rinc-XOA)) also has some discussion about `Qynviper` in the context of Executable Research Objects in general, which may offer suggestions about other `VM` use-cases for `RedPatch` in the future.

---

With all that said, describing code libraries in `Markdown` takes much less time than implementing them in `C++`, and this detailed summary perhaps gives a misleading sense of maturity and polish.  Once again, this should be considered Work In Process, and most of the code was developed when the long-term goal was publishing a single book, article, or data set, not to create a general-purpose library.  If you're a `C++` programmer with a history of cloning `github` repos, you've probably found many high-quality libraries supported by multiple codewriters and/or institutions.  Bear with me insofar as `RedPatch` and `DogLeash` are not that, not quite, though hopefully they can evolve in that direction.

To compensate for the incomplete nature of the code published here, hopefully there are some technical ideas that programmers or computer scientists might find interesting.  Some of this code simply addresses lapses that I don't really understand -- I don't know for instance why nobody though to build `DCMTK` exporters when `MI-CDM` was finalized, or build native `OpenMRS` renderers modeled after the now-defunct `FreeMedForms` (or why `FreeMedForms` is defunct in the first place), or why `Inria` hasn't updated `medInria` to `Qt6` (and in fact you have to compile *exactly* 5.15.13), or why `DICOM` annotations are not readily compatible with non-radiological image-annotation formats, or why there's no `Qt` digital map application template like `Poppler` is to `PDF` (this is one rare case where the open-source alternative -- `QGIS` -- is much worse than the commercial behemoth, `ArcGIS`).  But these probably aren't "interesting" topics in the sense that `C++` gurus would find new ideas in any code that plugs these holes.

But I think `RedPatch` and `DogLeash` are more interesting where they touch on `C++` interop and, in particular, Compiler Theory.  In other words, the `VM` system put to practical use has some technical differences with respect to rough analogies like `LuaVM`, `Pycode`, `AngelScript`, or `Jank` Intermediate Representation.  A little weird, perhaps, but interesting, I hope.
